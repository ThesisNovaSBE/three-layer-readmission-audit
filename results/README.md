# Results

Committed aggregate metrics — **no patient data, no MIMIC identifiers**.

Files placed here are version-controlled snapshots of model performance. They
are safe to commit because they contain only aggregate statistics (AUROC,
recall, counts, percentages), never row-level patient records.

> **Canonical vs. curated.** `models/*.json` written by the pipeline are the
> **canonical** result files (the code's own output, regenerated by a run).
> `results/` is a **curated, committed copy** of the thesis-relevant subset —
> a stable, citable snapshot. A copy in `results/` must be **byte-identical**
> to its `models/` counterpart (enforced by
> `tests/test_results_models_parity.py`). When updating, always copy from
> `models/` to `results/`, never edit a `results/` file by hand. See `README.md`.

**`xgboost_metrics.json`** (added 2026-09-05) is the real Stage 1 retrain —
400-trial Optuna search, capacity-constrained threshold, isotonic
calibration, targeting unplanned readmission (AUROC 0.7215, AUPRC 0.3965 on
the held-out test set). See `MODEL_CARD.md` for the full breakdown.

**`stage2_evaluation.json`** (rerun copy, refreshed 2026-11) — the current
Clinical-Longformer on the flagged+noted group, unplanned-label + corrected
age-group oversampling + 4096-token window + Platt recalibration. This copy is
the **rerun** (flagged-group recall 0.987, precision 0.434, ECE 0.084); it
replaced an earlier copy that still held the pre-recalibration run
(recall 0.974, ECE 0.196). AUROC/AUPRC (0.622 / 0.538) are unchanged — the
model is the same; only the Platt calibration and operating point moved.

**`pipeline_evaluation.json`** (added 2026-10-08, rerun merged
2026-11-21) — the real RQ1 + RQ3 result: Stage 1 alone, Stage 2 alone,
full pipeline, control arm, the conditional-triggering post-hoc
analysis, and the secondary both-override policy, all from the completed
full Stage 3 batch rerun (2026-11-21, all 9,899 flagged+noted
admissions). The headline: at matched alert volume, adding the full
cascade does not improve on Stage 1 alone. The proper test is the paired
pipeline-minus-control bootstrap (`pipeline_paired_differences.json`,
`scripts/compare_pipeline_control_paired.py`): the **precision difference is
−0.0048 (95% CI [−0.0085, −0.0015], excludes zero)** and the **recall
difference is −0.0035 (95% CI [−0.0076, +0.0003], includes zero)** — i.e. the
cascade's precision is lower than Stage 1 alone and its recall is not
distinguishable from it. See `MODEL_CARD.md` for the full writeup.

**`selection_bias_evaluation.json`** (added 2026-10-26) — does the
~60% of Stage 1's test partition with a discharge note (the population
RQ1–RQ3 are evaluated on) differ systematically from the ~40% without
one? Yes, demographically: the notes-covered group is older, sicker,
and far more often an emergency admission. No, in outcome rate: the
readmission rate itself is nearly balanced between the two groups
(SMD=0.053, below the conventional 0.1 imbalance threshold). See
`MODEL_CARD.md`'s "Selection bias" section.

**`planned_return_crosscheck.json`** (added 2026-10-26, rerun
2026-11-21) — does Stage 3's note-derived `planned_return` field agree
with the structured, `admission_type`-based "unplanned" proxy? Not
reassuringly: 93.4% raw agreement is still *below* the 95.8% a trivial
"always predict unplanned" baseline would score. In the rerun the
tighter `planned_return` definition brings the LLM's "planned" rate onto
the structured proxy's (4.2% vs 4.2%, down from 19.2% vs 4.2% in the old
run), but the two still disagree substantially on *which* admissions are
planned. Reported as an open, unresolved discrepancy, not evidence
either signal is simply wrong. See `MODEL_CARD.md`'s `planned_return`
section.

**`stage3_validation_controls_summary.json`** (RQ2) — the robustness
controls testing whether Stage 3 actually uses its inputs, on four control
arms over 150 admissions. Note-withheld: `insufficient_evidence` on 150/150
(the auditor abstains without the note). Stage-2-withheld: 89.3% agreement
with the reference arm (removing Stage 2 shifts ~11% of decisions toward
uphold). Repeated reference: 100% decision agreement on identical inputs.
The reference arm reproduces the main run on 145/150 decisions (96.7%; the
gap is the bf16 batching effect). Committed **without** any `sample_hadm_ids`
(MIMIC-IV-Note DUA — the identifiers were removed on the cluster); run
`python -m scripts.check_results_no_identifiers` on it before committing.
See `MODEL_CARD.md`'s RQ2 section.

> **Provenance of the 145/150 (96.7%) reference-arm-vs-main-run figure.** This
> value is **not stored in any committed JSON** and cannot be recomputed from
> the repo: it was measured on the cluster by validation job **17462868**
> (`scripts/run_validation_controls.py`, which compares the reference arm's
> per-admission decisions against `stage3_batch_results.csv`), and those
> per-admission CSVs are gitignored under the DUA. It is quoted here and in the
> docs as a measured value with this source, not re-derived.

**`batch_size_comparison.json`** (RQ2) — the batch-size check: the first 20
admissions re-audited one at a time vs. the main (batched) run.
decision_model 100%, decision_rule 100%, grounds 65% — batching leaves the
decisions unchanged but moves which grounds are extracted on about a third of
admissions. (The acceptance arm test, first 8 admissions, passed 8/8.)

**`discordance_sensitivity.json`** (added 2026-10-08) — the

**`discordance_subgroup_evaluation.json`** (added 2026-10-08) — the

the concordant and discordant subgroups. By F2, Stage 3 underperforms

`MODEL_CARD.md` and `scripts/analyze_discordance_subgroups.py`.

(session 16) because its schema predated the current Stage 3 design

`docs/ARCHITECTURE.md` §2) and no longer matched the code that would

## How to update

After a training/evaluation run produces a metrics file in `models/` (e.g.
`models/stage2_evaluation.json`, `models/xgboost_metrics.json`) that you want
as a permanent, citable snapshot, copy it here and commit it:

```bash
cp models/<file>.json results/<file>.json
```

`tests/test_results_models_parity.py` fails if any file present in both
folders differs, so a `results/` copy can never silently drift from its
`models/` source.

The `models/` directory version may be overwritten by future runs; the
`results/` copy is the permanent record — so only copy a file here once
you're confident its schema and numbers are current (check
`docs/ARCHITECTURE.md` first).
