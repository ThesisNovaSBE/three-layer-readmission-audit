## Key decisions / findings

- **Job 16119168 results: 2 of 3 fixes confirmed, 1 not.**
  `all_quotes_verified` went from 0% to 76% (whitespace-normalization fix
  works) and mid-word justification cutoffs went from several to 0/50. But
  `strong_discharge_support` fired on 47/50 patients (94%) — *worse* than
  the pre-fix 62 total citations — including citing the bare "Discharge
  Disposition: Extended Care" field, the exact pattern an explicit negative
  example in the prompt already excluded. Conclusion: a prose "ALL THREE,
  not just one" requirement doesn't reliably stop a 27B model from treating
  one weak signal as sufficient, even with a negative example already
  present.
- **Fixed by moving the compound logic to code (same pattern as
  `decision_rule`).** `strong_discharge_support` removed from
  `MITIGATING_GROUNDS` (the model-citable taxonomy, now 3 entries not 4).
  The model instead extracts three atomic quotes independently
  (`followup_plan_quote`, `named_caregiver_quote`, `clinically_stable_
  quote`, each `""` if not documented); `_extract_discharge_support_ground`
  credits the combined ground only when all three are present and
  individually verified via `verify_quote`. Extracted `compute_discordance`/
  `sweep_discordance_thresholds`/`DISCORDANCE_MODES` into a new
  `src/stage3/discordance.py` purely to keep `explain.py` under pylint's
  1000-line cap after the taxonomy split — no behavioral change.
- **Logic-soundness review (round 1) found one critical bug**:
  `decision_rule` — documented everywhere as "a fully transparent fallback
  the model can't fabricate its way past" — was being computed from the
  *raw* mitigating/aggravating lists, including grounds whose quotes failed
  `verify_quote`. A single hallucinated ground could still flip the
  deterministic decision, silently defeating the one guarantee that
  mechanism exists to provide. Fixed: `_finalize_annotation` now filters to
  quote-verified grounds only before calling `compute_decision_rule`;
  `all_quotes_verified` still reports over the full list (a deliberately
  different, looser transparency metric — how much of everything cited
  checks out, vs. what the safe verdict is using only evidence that does).
  Also fixed a smaller, confirmed-real issue in the same pass: the model
  citing the same ground twice with different quotes (observed in real
  output — `cognitive_impairment` cited twice for one patient), which
  double-counted in ground-frequency statistics without adding information.
  `_validate_grounds` now dedupes to the first occurrence.
- **Operational-robustness review (round 2) found one bug that would have
  blocked the real run outright, plus one silent-data-loss gap.**
  1. `scripts/slurm_stage3_batch.sh`'s preflight check hardcoded the OLD
     repo-relative MedGemma weights path
     (`models/medgemma-27b-text-it/*.safetensors`) from before the
     2026-09-18 storage migration; `config.yaml`'s real
     `stage3.model_name` has pointed at KISSKI project storage since then.
     This would have failed `exit 1` on every one of the ~5 job
     resubmissions the full run needs, each time after paying a queue-wait
     cost that has hit 30+ hours once already this project. Fixed to read
     the path from `load_config()` directly so it can't drift out of sync
     with the config again.
  2. A `_prepare_patient` failure (missing note, malformed feature row —
     deterministic, not transient) was only printed to the job log, never
     written to the output CSV. Across a run needing several chained
     `--resume` resubmissions over days, that admission would fail
     identically and be retried forever, and there would be no way to
     verify "every one of ~9,899 target admissions is accounted for" from
     the CSV alone. Fixed: every target `hadm_id` now gets exactly one row
     always (`ok`, LLM-`annotation_failed`, or now also prep-
     `annotation_failed`, clearly labeled). Deliberately did NOT apply the
     same fix to whole-chunk `call_llm_batch` failures (e.g. OOM) — that
     failure mode is plausibly transient (VRAM fragmentation, a flaky
     serving hiccup), and a fresh process on the next resubmission has a
     real chance of succeeding; writing a permanent failure row there would
     prevent a beneficial retry. The asymmetry is intentional.
  3. Added `TIME_LIMIT` to `--mail-type` — every job segment but the last
     will end via timeout, not completion, and some SLURM configs don't
     fire `END` for a `TIMEOUT` state.
  4. Considered and explicitly rejected (per user's call): self-chaining
     job resubmission (`sbatch --dependency=afterany` submitted from
     within the job). Would eliminate the queue-wait gap between manual
     resubmissions, but risks silently crash-looping through the core-hour
     budget if something is systematically broken. User chose to keep
     resubmission manual.

## What works now

- `strong_discharge_support` can no longer be credited from a single weak
  citation — requires three independently-verified pieces of evidence.
- `decision_rule` can no longer be flipped by a fabricated ground on either
  side — the "model can't fabricate its way past this" claim is now
  actually true, not just documented as true.
- Ground-frequency statistics no longer double-count repeated citations.
- The full run's SLURM script will actually pass its preflight check.
- No admission can be silently dropped and retried forever across the
  run's several chained job resubmissions — every target gets exactly one
  CSV row, always.
- Full local test suite (181 passed) and pylint (10.00/10) clean throughout.

## What's broken / open problems

- **None of this round's fixes have been re-verified against a fresh
  cluster run yet.** A third 50-patient validation is the natural next
  step, specifically to check whether `strong_discharge_support`'s firing
  rate actually drops now and only triggers on genuine three-criteria
  evidence.
- Two residual, lower-probability operational risks noted but not
  engineered around this session (given the imminent run and the cost of
  further hardening): (1) CUDA memory fragmentation degrading over many
  thousands of generate() calls across a multi-day run — likely mitigated
  in practice by the walltime-driven resubmission cadence already forcing
  periodic fresh processes, but unconfirmed; (2) a single pathological
  prompt causing a reproducible whole-chunk generation failure (as opposed
  to transient OOM) would currently retry forever every resubmission,
  since chunk-level failures are deliberately not written as permanent
  rows — if the SAME chunk of hadm_ids fails across multiple job logs,
  that's the signal to manually isolate and rerun them one at a time.
- Still open, unchanged from session 25: `bootstrap.py`'s resampling
  performance, D1/D2/D3 validation controls unexecuted, discordance
  threshold unvalidated, frontend `stage2_confirmed` gating, the thesis
  `.tex` document itself.
