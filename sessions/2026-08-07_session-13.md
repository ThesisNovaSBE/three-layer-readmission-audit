### FastAPI backend (frontend-restructuring)

Built `api.py` at the project root. Four endpoints:

- `GET /api/health` — status, patient count, `artifact_loaded`, `demo_mode`
- `GET /api/patients[?confirmed_only=true]` — Stage-2-flagged patients with clinical fields merged in from the feature matrix
- `GET /api/patients/{hadm_id}` — single patient record
- `POST /api/patients/{hadm_id}/explain` — on-demand Stage 3 call (phi4-mini via Ollama)

All heavy objects (XGBoost artifact, Stage 2 results, feature matrix, calibration thresholds) are pre-loaded once in the FastAPI `lifespan` context and passed into every explain call — no per-request load cost.

Demo mode: if `stage2_results.csv` is absent (Stage 2 not yet run), the server derives a patient list by running Stage 1 predictions on the feature matrix. This lets the frontend be tested end-to-end with synthetic data without needing real MIMIC notes.

## Key decisions made

- **Stage 3 is on-demand only.** No batch processing. A clinician clicks "explain" in the frontend for a specific patient; the API triggers phi4-mini. This was already decided in the previous session.
- **XGBoost artifact loads first in lifespan** — importing torch after `joblib.load` on macOS ARM causes SIGSEGV (MPS conflict). The lifespan respects this order.
- **Demo mode is automatic.** The server detects missing `stage2_results.csv` and falls back gracefully rather than refusing to start. Frontend shows `demo_mode: true` from the health endpoint.
- **fastapi/uvicorn/starlette added to pylintrc `ignored-modules`** — these are runtime deps, not available in the lint environment.
