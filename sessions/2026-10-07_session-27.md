## Key decisions / findings

- **Third 50-patient validation (job 16270320) found and fixed two more
  real bugs before the full run could safely start:**
  1. **Truncation regression from the discharge-support fix itself** — the
     three new atomic quote fields (`followup_plan_quote`, etc.) had no
     `max_length` cap, unlike every other free-text field in the schema.
     One real patient's `clinically_stable_quote` got stuck in a
     degenerate repetition loop, burning the entire 4096-token budget and
     never reaching `decision` — 4/50 patients failed this way. Fixed with
     `max_length=400`, same pattern as `clinical_justification`.
  2. **Ground-quote semantic mismatch** — the model citing a real,
     verbatim quote under the wrong ground (e.g. a disease-progression
     sentence cited as `planned_return`). `verify_quote` only confirms a
     quote is genuine text from the note, not that it supports the ground
     it's attached to. Added an explicit prompt instruction against this;
     confirmed in the next validation run (job 16271359) that this helped
     but did not eliminate the pattern (~2% of citations across 50
     patients were still mismatched or borderline) — documented as an
     accepted, quantified residual limitation rather than chased further,
     per explicit user decision (AskUserQuestion) given diminishing
     returns and no clean code-side fix available (no enumerable
     substructure to verify against, unlike the discharge-support fix).
  3. **A real, instructive case of `decision_rule`'s own limitation**:
     patient `20024137`'s `decision_rule` said `override` on a weak,
     inferential `planned_return` citation ("prior cycles complicated by
     febrile neutropenia" — about a past complication, not a documented
     future appointment) while `decision_model` correctly upheld despite
     having the same evidence. Worth keeping for the thesis discussion:
     `decision_rule` isn't strictly more trustworthy than `decision_model`,
     just differently reliable — it can't be fabricated past, but it also
     can't judge whether genuinely-verified-but-weak evidence should
     actually carry a decision.
- **Two real operational bugs found and fixed mid-run, both confirmed via
  live evidence, not guessed:**
  1. `_setup_batch` crashed (`ValueError: No discharge notes found after
     filtering`) when `--resume` found zero admissions pending — a real,
     reproducible state (not hypothetical) hit on the very first resubmit
     attempt after `--resume` correctly saw everything already done.
     Fixed: skip note preload entirely when `pending` is empty.
  2. An apparent "41 duplicate rows" discrepancy turned out to be a false
     alarm caused by using `wc -l` to estimate CSV row count —
     `annotation_failed` rows contain raw truncated JSON text with literal
     embedded newlines, which `wc -l` miscounts as extra rows despite
     being correctly CSV-quoted. `pandas.read_csv` (used internally by
     `_already_done()`) parsed it correctly the whole time; there was
     never an actual duplication bug. Switched to a pandas-based progress
     check for the rest of the run to avoid repeating this scare.
- **Queue congestion was real and significant this run** — one segment
  queued for ~37 hours before starting. Used `sbatch --dependency=afterany:
  <jobid>` to pre-queue each next segment immediately rather than waiting
  to notice a segment had ended before resubmitting — safe (SLURM holds a
  dependent job ineligible for scheduling until the dependency resolves, no
  concurrent-write risk) and removed the idle gap between segments ending
  and the next one entering the real queue. Kept resubmission itself
  manual per the user's explicit call in session 26 — this is a partial,
  one-hop version of that, not the fully automatic self-chaining option,
  which stays rejected for the stated reason (a systematic failure could
  otherwise crash-loop through the core-hour budget unattended).
- **The full run completed cleanly**: 9,899/9,899 unique admissions
  (confirmed no duplicates), `COMPLETED` state on the final segment (not
  another timeout), 93 annotation failures (0.94%, consistent with the
  final validation run's rate). Final decision distribution: 7,015 uphold,
  2,778 override, 13 insufficient_evidence, 93 failed.
- **`evaluate_pipeline.py`'s patient-clustered bootstrap CIs (1000
  resamples, 4 calls on the full 104,242-admission cohort) took ~2h15m
  real wall-clock time** — the unfixed `bootstrap.py` performance issue
  flagged (but left unfixed) in session 25 turned out to matter for real
  this time, not just for a skippable sanity check. Ran it as a proper
  CPU-only `sbatch` job (no GPU needed) rather than foreground on the
  login node, after catching that it had been started that way — `sacct`
  showing `TotalCPU=0:00:00` on a genuinely live, 99.7%-CPU process turned
  out to be a reporting artifact for still-running jobs on this cluster,
  not a hang; `ps` on the allocated node was the reliable check.
- **The real RQ2 result: blanket Stage 3 auditing underperforms Stage 1
  alone at matched alert volume.** Full pipeline: precision=0.435 [0.417,
  0.457], recall=0.295 [0.276, 0.315]. Control arm (Stage 1 alone, same
  12.9% alert budget): precision=0.450 [0.433, 0.469], recall=0.316
  [0.298, 0.338]. The recall gap looks real (control's CI lower bound sits
  above the pipeline's own point estimate); precision CIs overlap more.
  This is a legitimate, reportable negative result — the auditor's
  overrides are, on net, cancelling more correct alerts than they're
  correctly catching, when applied to every flagged admission
  indiscriminately.
- **A post-hoc conditional-triggering re-analysis clarifies why.** Treating
  CONCORDANT admissions as if Stage 3 had never been called (Stage 1's
  flag simply stands) while DISCORDANT admissions keep their real Stage 3
  decision improves both precision and recall versus the blanket run
  (0.437/0.319 vs 0.435/0.295) using 4,662 fewer LLM calls (48% reduction)
  — evidence the harm concentrates specifically in auditing concordant
  cases, not in auditing per se. This was deliberately computed post-hoc
  from the completed blanket run (a session-19 decision, re-confirmed this
  session when the user independently arrived at the same question) rather
  than by restricting the real run to discordant-only from the start —
  doing it this way means the concordant cases' real Stage 3 decisions
  exist to check against, rather than trusting the discordance heuristic
  on faith. Two honest caveats: its alert volume (13.9%) is ~1 point above
  the matched-budget comparisons, which is part of the mechanism but means
  it isn't a perfectly volume-matched comparison; and no bootstrap CI has
  been computed for it yet, so "better than blanket" is a point estimate,
  not yet a statistically tested claim.
