code change needed there, only two documentation citations added.

## Key decisions / findings

- **`~/thesis` on the cluster was a plain rsync'd copy, not a git clone** —
  no `.git` at all. Turned it into a real checkout in place
  (`git init` + `git remote add` + `git fetch` + `git checkout -f -b
  training-changes origin/training-changes`), which is safe here because
  `.env`, `.venv/`, `data/`, and `models/**/*.joblib|*.pt|*.safetensors` are
  all gitignored — only tracked code files were overwritten. Backed up
  `models/` and `.env` first as insurance regardless.
- **Unversioned `module load miniforge3` silently no-ops on this cluster**
  (no default version marked) — `conda`/`python` end up not on `PATH` with
  no error at load time. This bug was already present in `train_stage2.sh`
  and `diagnose_cluster.sh` too, not just the Stage 1 script; all three
  fixed to `module load miniforge3/24.3.0-0`. Plausibly part of what caused
  the "errors all the time" on the user's first real KISSKI attempt.
- **`set -u` (nounset) killed the Stage 1 job in 25 seconds**, before any of
  the script's own commands ran — `thesis-env`'s conda activation hook
  (`libblas_mkl_activate.sh`) references `$MKL_INTERFACE_LAYER` without a
  default, which `-u` treats as fatal. Confirmed via a real failed job
  (15700175), not guessed. Fixed to `set -eo pipefail` (dropped `-u`).
- **`XGBClassifier(n_jobs=-1)` oversubscribed CPUs under concurrent tuning**
  — every one of the 8 concurrent Optuna trials requested all 16 allocated
  cores, i.e. up to 128 threads contending for 16 cores. Found by re-reading
  `models.py` before resubmitting, not from a failure. Fixed
  `build_estimator` to divide `os.cpu_count()` by `cfg.stage1.tune_n_jobs`;
  no effect on `train.py`/`evaluate.py`'s single-fit calls since
  `tune_n_jobs` defaults to 1 there.
- **`--time=08:00:00` was nowhere near enough** — job 15700645 (first clean
  run after all the above fixes) completed 140/400 trials in ~7.5h before
  being killed by the wall-time limit (confirmed genuinely working the
  whole time: `nvidia-smi` showed 39% GPU util + an active process, and the
  Optuna journal file was growing). ~19 trials/hour → full search needs
  ~21h. Bumped to 24h. Resubmitted once accidentally with the *old*
  8h script (forgot to `git pull` on the cluster before resubmitting) —
  caught via `sacct`/`grep time= scripts/slurm_stage1_tune.sh`, pulled, and
  resubmitted correctly. Nothing was lost either time — Optuna's
  `JournalFileBackend` + `load_if_exists` in `tune.py` means every resubmit
  resumes from the recorded trial count instead of restarting.
- **Full Stage 2 code audit** (`setup_stage2.py`, `src/stage2/{dataset,
  splits,train,calibrate,evaluate,predict,_utils}.py`, `train_stage2.sh`,
  `config.yaml`'s `stage2:` block) before queuing it, same reasoning as
  session 21's Stage 1 pass — the user wanted it "tested completely" given
  Stage 1 alone took three submissions to get running. No bugs found in the
  Python beyond what's listed below; the design (patient-level splits,
  focal loss, per-age-group weighting, Platt calibration per band,
  checkpoint-resume, offline-mode env vars) matches
  `docs/ARCHITECTURE.md` §2/§4 exactly — retraining Stage 1 then Stage 2 at
  `max_seq_length=4096` is explicitly the documented next step ("no script
  changes needed, just a fresh KISSKI/Grete job"), not a deviation from plan.
- **`TOKENIZERS_PARALLELISM` unset** — `dataloader_num_workers=8` forks 8
  worker processes that each touch the fast Rust-backed tokenizer, a
  known combination that warns or (on some versions/platforms) deadlocks
  under fork-based multiprocessing, the default on Linux. Not a confirmed
  failure here, but cheap and safe to disable preemptively — added to
  `train_stage2.sh` alongside the existing offline-mode env vars.
- **Stage 2 depends on Stage 1's artifact, not just as a preflight check** —
  `build_splits` reads the *exact* `train_idx` baked into
  `models/stage1_<model>.joblib` to keep Stage 1's test partition
  out-of-sample for Stage 2 too. An old (June) artifact already on the
  cluster would pass `train_stage2.sh`'s preflight check, but training
  against it risks a stale split now that cohort/label logic has changed
  since June. Recommended: use `sbatch --dependency=afterok:<stage1_jobid>`
  to queue Stage 2 now without it actually starting before Stage 1's fresh
  artifact exists — not yet submitted as of this log (waiting on the user
  to confirm the current Stage 1 job ID and check
  `models/clinical_longformer/` actually has the real downloaded weights,
  not just the git-tracked tokenizer config files, since
  `train_stage2.sh`'s existing preflight check only verifies `config.json`,
  which is committed to git and would exist either way). **Resolved same
  day**: added a real weight-file check (`model.safetensors`/
  `pytorch_model.bin`, not just `config.json`) to `train_stage2.sh`'s
  preflight, and wired `predict_stage2_all` into the same job so it produces
  the population-wide (RQ1-comparable) scoring automatically, not just the
  Stage-1-flagged-only cascade scoring `setup_stage2.py` does by default.
- **CRITICAL, found by the audit fork: the model has always trained on the
  all-cause label, not unplanned, despite every doc (`MODELING_PLAN.md`'s
  scope line, `THESIS_NARRATIVE.md`'s opening framing, `MODEL_CARD.md`'s
  "Primary use") stating the study targets *unplanned* 30-day readmission.**
  `readmission_30d_unplanned` was added to the feature matrix in an earlier
  remediation review (P7b) but never wired into `split_xy()` or any Stage 2
  module — `docs/ARCHITECTURE.md` even self-discloses this ("not yet used
  anywhere... future analysis, not automatic"), but the docs' framing
  language was never reconciled with it. This affected every Stage 1 model
  this project has ever produced, including the job that had been running
  for ~9h at the time this was found. User's call: all-cause is "fatal,"
  fix it — killed the running job and switched the whole pipeline's target.
  Fix: `src/schemas.py` gets a new `MODEL_TARGET_COL = TARGET_COL_UNPLANNED`
  — the single place that decides which of the two label columns
  (`TARGET_COL`/`TARGET_COL_UNPLANNED`, both still computed by
  `compute_readmission_label()` unconditionally, unchanged) is actually the
  model's target. `features.py`'s `split_xy()` now reads `MODEL_TARGET_COL`.
  Every Stage 2 module that imported `TARGET_COL` as "the label" (`dataset,
  splits, train, calibrate, evaluate, predict`) now imports
  `MODEL_TARGET_COL as TARGET_COL` instead, so Stage 2 fine-tunes/calibrates/
  evaluates against the same target Stage 1 now uses, not a mismatched one.
  `cohort.py`, `stage3/pipeline.py`, and `setup_demo.py` deliberately left
  on the literal all-cause `TARGET_COL` — general cohort/demo reporting, not
  model training.
- **CRITICAL, found while fixing the above: switching the target silently
  invalidates cached state in both stages, and nothing was checking for
  it.** `src/stage2/splits.py`'s `build_splits()` cached its output CSVs
  keyed only on file existence, with no check that they came from the
  *current* Stage 1 `train_idx` or target column — and since `~/thesis` on
  the cluster was an old rsync'd copy (this log, above), gitignored dirs
  like `data/processed/` could carry state across completely unrelated
  runs. Same issue in `src/stage2/train.py`'s checkpoint-resume (blindly
  resumed from whatever was newest, no identity check) and in
  `src/model/tune.py`'s Optuna journal (the ~290-trial journal already on
  disk was scored against the *old* all-cause objective — resuming it under
  the new target would have silently mixed incompatible trial results).
  Fixed all three with the same pattern: a fingerprint (Stage 1 `train_idx`
  hash + target column, or just the target tag for Optuna) saved alongside
  the cached state; a mismatch means rebuild/restart fresh instead of
  trusting what's there. Stage 2's stale checkpoints are moved aside
  (`stage2_checkpoints_stale_<timestamp>/`), not deleted or silently
  overwritten. Optuna's journal filename/study name now embeds the target
  tag directly, so a target switch just starts a new study under a new
  filename rather than needing runtime comparison logic at all.

**The `config.yaml` rebalance, in full** (user explicitly confirmed this
approach over two alternatives — see conversation): computed real Stage 1
train-partition note-matched counts per (age_band, unplanned-label) cell
using the actual local MIMIC-IV data on this Mac (not an estimate):
`18-40: 7,909 pos / 33,948 avail`, `41-55: 11,777 / 44,813`,
`56-70: 15,755 / 61,623`, `70+: 14,065 / 61,297`. The old targets (all
sized against the all-cause label, before P7b even existed) requested more
positives than exist everywhere, worst for 70+ (only 46.9% of its 30,000
target available) — and because 70+'s *negative*-cell target (62,000) was
simultaneously almost exactly achievable (61,297 available), the silent
per-cell fallback inverted the design: 70+ landed at 18.7% positive in the
actual training sample, the *lowest* of all four bands, versus ~24% for
the other three — backwards from "70+ is deliberately oversampled to
address the recall gap found in the v1 model." Rebalanced every `"_1"`
target to its exact real ceiling and scaled every `"_0"` target to
reproduce each band's *original* intended positive ratio against that
ceiling — 70+ is now correctly the highest (32.6%) of all four bands
again, as designed. Total training notes drops from ~223k (what was
silently happening, by accident) to ~166,787 (deliberate, documented).
