## What I worked on

Added parallel range-job support to the Stage 3 batch runner so the final audit
can be produced as one sequential job plus several range jobs and merged, while
the existing full run (job 17327544) keeps running unaffected. Plan approved
first; nothing committed.

## Key decisions made

- **Backward compatible / running-job safe:** with no new flags,
  `src.stage3.batch` behaves exactly as before. The already-running sequential
  job has the module loaded in-process and writes `stage3_batch_results.csv`;
  range jobs write different files (or the gap job writes the main file only
  after the sequential job, with `--resume`), so there is no collision.
- **Range selection (`--range-start S` / `--range-end E`, E exclusive):** pure
  functions `select_range` / `validate_range` in a new
  `src/stage3/_ranges.py` (same private-module extraction pattern as
  `_stopping.py` / `_notecap.py`, done to keep `batch.py` under the 1000-line
  cap -- it was 985 after). S and E must be multiples of the generation batch
  size, except E may equal the total target count; validated against the
  effective batch size. Mutually exclusive with `--limit`. Because a fresh
  range's pending list is exactly `targets[S:E]` and S/E are batch-aligned,
  chunking from index 0 reproduces the sequential run's chunk groups --
  identical bf16 batch composition.
- **Cohort invariant:** `_cohort_scores` ranks against the full `results_df`
  (`stage2_results.csv`), independent of the audited slice, so r1/r2 and the
  discordance category are unchanged by a range -- confirmed by a test that the
  cohort DataFrame handed to `_prepare_patient` is the full four admissions
  while only the slice is prepared.
- **Range output + per-file guards:** with no `--out` and a range set, defaults
  to `models/stage3_batch_results.range{S}-{E}.csv` (+ `.raw.jsonl` sidecar).
  Resume, stale-output guard, cut-off-line guard, and the fail-fast *trigger*
  are per output file automatically. The fail-fast *marker*
  (`models/stage3_FAILFAST`) stays shared, as agreed -- any segment failing
  >20% halts all new submissions via the SLURM preflight.
- **`scripts/slurm_stage3_range.sh`** `sbatch ... S E [OUT]`: mirrors
  `slurm_stage3_batch.sh` (resources, env, preflight incl. the FAILFAST
  start-check). `#SBATCH --time=32:00:00` default, overridable on the sbatch
  CLI. `#SBATCH` can't see positional args, so the per-range log (name contains
  S and E) is opened by the script via `exec` after a `%j` bootstrap log.
- **`scripts/merge_stage3_parts.py`** (CPU only, no torch): identical-header
  check, union-of-hadm_ids == full target set (same completeness logic as the
  validation script), main-file precedence on duplicates (count reported),
  writes in original target order via a temp file after backing up the unmerged
  main to `stage3_batch_results.premerge.csv`; merges the `.raw.jsonl` sidecars
  the same way. Exit 1 on any failed check.
- **`slurm_stage3_validation.sh`:** unchanged -- the merged output lands at the
  canonical path, so the arm test (first 8), bs1 check (first 20), and
  completeness guard all work as-is.
- **MODEL_CARD.md:** one paragraph on the sequential + batch-aligned range jobs
  + merge; states batch composition equals a single sequential run but does
  **not** claim bit-identical output across GPU nodes.
