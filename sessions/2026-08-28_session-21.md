## Key decisions / findings

- **GPU utilization**: a single XGBoost fit on this dataset (~521k rows, ~40
  features) is small relative to an A100 — running Optuna trials one at a
  time leaves most of the GPU idle regardless of `device=cuda`. Added
  `stage1.tune_n_jobs` to run several trials concurrently against the same
  GPU. This required switching Optuna's persistent storage from sqlite to
  `JournalFileBackend` — sqlite's file locking is unreliable on NFS-style
  shared filesystems (like KISSKI/Grete project directories) under
  concurrent writers; Optuna documents JournalFileBackend as the fix for
  exactly this. Verified both storage switch and concurrency by actually
  running the search twice (fresh + resume) with `--tune-n-jobs 3`.
- **`setup_demo.py` was completely broken** — `cfg["data"]["synthetic_n_patients"]`
  dict-style access on `AppConfig` (a Pydantic model with no `__getitem__`).
  Exact same bug class already known to have broken `train_stage2_gpu.py`
  (deleted in an earlier session) and documented in the recovered
  `HPC_DEPLOYMENT.md` troubleshooting table as a real prior KISSKI failure.
  Fixed to dot-access; verified by actually running `python setup_demo.py`
  end to end.
- **`src/data/features.py` had no `argparse` at all** — the SLURM script's
  `python -m src.data.features --mode full` was silently swallowed as an
  unparsed argument, no error, no effect. Turned out not to corrupt data
  (the build path doesn't subsample by mode regardless), but the CLI flag
  looked functional while doing nothing. Added proper `--mode` handling for
  honesty/consistency with the other Stage 1 CLIs.
- **`_find_resume_checkpoint` (Stage 2) sorted checkpoint directories
  lexicographically**, but HuggingFace names them `checkpoint-<step>` with
  no zero-padding — `"checkpoint-500"` sorts *after* `"checkpoint-1500"` as
  a plain string. On a real multi-hour run this would silently resume from
  an older checkpoint than the true latest, discarding completed training
  time without any error. Fixed to sort by the numeric step. Added
  `tests/test_stage2_train.py` (the first test file Stage 2 has ever had) —
  regression-tests this specifically, plus the empty/missing-dir cases.
- **`evaluation_strategy` doesn't exist in Transformers 5.x** — `requirements.txt`
  pins `transformers>=4.36` with no upper bound, so a fresh
  `pip install -r requirements.txt` today resolves to Transformers 5.16.1
  and `evaluation_strategy` (which `_build_training_args` hardcoded) has
  been removed entirely, not just renamed/deprecated as the old code
  comment assumed. Confirmed by actually installing transformers 5.16.1 and
  torch locally and constructing a real `TrainingArguments` — it raised
  before the fix, succeeded after. Fixed by detecting which kwarg name
  (`eval_strategy` vs `evaluation_strategy`) the installed version actually
  accepts at runtime, so this can't silently break again on either side of
  that version line. Also bumped `accelerate`'s floor (`>=0.27` →
  `>=1.1.0`) — confirmed the old floor is insufficient for Transformers 5.x's
  Trainer (hit the real `ImportError` locally before fixing it).
- **Found, not fixed — needs the user's confirmation**: `scripts/slurm_stage1_tune.sh`
  uses `module load anaconda3` + `conda activate thesis`, while every other
  cluster script (`download_model.sh`, `train_stage2.sh`,
  `diagnose_cluster.sh`) uses `module load miniforge3` + `conda activate
  thesis-env`. Can't verify from here whether Grete (Stage 1's cluster)
  genuinely needs a different module/env than KISSKI (Stage 2's), or
  whether this is just a leftover inconsistency from whenever
  `scripts/slurm_stage1_tune.sh` was first written. Not changed without
  confirmation — a wrong guess here is exactly the kind of thing that
  wastes a cluster submission.
