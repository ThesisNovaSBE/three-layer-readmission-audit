## Key decisions / findings

- **The vLLM/MedGemma smoke test failed, repeatedly, for a chain of
  distinct real bugs** (each fixed and verified before moving to the
  next): wrong target column silently emptying every discharge note
  (`TARGET_COL` vs `MODEL_TARGET_COL`, same class of bug as session 22/23's
  staleness fixes, just in a new spot); an attention-extraction tensor
  shape assumed backwards since the code was first written (`(batch,
  heads, num_global, seq_len)` vs. the actual `(batch, heads, seq_len,
  num_global)`) — crashed every patient, confirmed via direct reproduction
  against the real trained Longformer, not guessed; a 391ms/call SHAP
  `TreeExplainer` rebuilt from scratch every patient instead of cached
  (~64 min of pure waste at full scale); a missing-vLLM `ImportError`
  silently swallowed and mislabeled as a per-patient annotation failure.
- **Then a genuinely structural CUDA problem, not a code bug.** `pip
  install vllm` silently upgraded torch to a CUDA-13-only build; the
  cluster's driver caps at CUDA 12.8 (confirmed identical on both the
  `kisski` A100 and `kisski-h100` partitions — not node-specific). Spent
  real time trying to downgrade vLLM to a version pinning an
  older, cu128-available torch (`vllm==0.22.0`, `torch==2.11.0+cu128`) —
  got past the driver check, but hit a second wall: `vllm`'s
  flashinfer/CUTLASS kernel dependencies (`nvidia-cutlass-dsl-libs-cu13`)
  have **no cu12 equivalent at all**, an unconditional CUDA-13 requirement
  regardless of vLLM/torch version. Confirmed via a "complete analysis"
  write-up (requested by the user after several days of this) that this
  wasn't fixable by further version archaeology.
- **Decision: drop vLLM, switch to plain HF `transformers.generate()` +
  `lm-format-enforcer`.** User-selected option after I laid out the
  alternatives (bare transformers + guided-decoding library vs. reverting
  to Ollama vs. continuing the version hunt). Same model, same bf16
  precision, same schema-constrained-JSON guarantee — only the serving
  mechanism changed. Verified locally before touching the cluster: the
  `torch_dtype`/`dtype` kwarg rename issue (used the more backward-
  compatible `torch_dtype`), and that the Longformer attention shape fix
  holds under both transformers 4.57.6 and 5.16.1 (not version-dependent,
  the original assumption was just wrong).
- **`lm-format-enforcer`'s actual importable module is `lmformatenforcer`**
  (no separators), not `lm_format_enforcer` — a real bug in my own first
  implementation, caught by the cluster smoke test, verified by installing
  the package locally and checking. Also confirmed its transformers
  integration submodule breaks under transformers 5.x (`PreTrainedTokenizerBase`
  moved) — must stay on the cluster's `transformers==4.57.6`.
- **First fully successful Stage 3 inference, then two more real bugs
  found from the actual output content, not crashes.** Once the import was
  fixed, generation worked but 7-8/8 patients hit `annotation_failed` —
  diagnosed from the raw truncated JSON (not guessed) as: (1) the 2048-
  token output cap being too small once grounds+quotes+justification are
  accounted for (raised to 4096); (2) even at 4096, MedGemma cites the
  same ground repeatedly with overlapping quotes instead of being
  selective — fixed by adding a hard `maxItems=3` JSON-schema constraint
  (enforced by guided decoding, not just a prompt instruction) on both
  grounds lists; (3) `clinical_justification` running past a thousand
  characters despite the prompt asking for "2-4 sentences" — fixed with a
  `maxLength=800` schema constraint. After both schema fixes: **8/8
  patients, 0 failed, 0 annotation_failed** — the first fully clean Stage 3
  run in this project's history.
- **Batching implemented, but its real payoff only showed up after the
  schema fixes.** Split `explain_patient()` into `_prepare_patient`/
  `_assemble_result` halves so `batch.py` can prepare a whole chunk of
  prompts and submit them to one batched `generate()` call
  (`call_llm_batch`, new). First batched run (before the maxItems/maxLength
  fixes) showed no speedup at all — 37.5 min for 8 patients, same as
  unbatched — because every sequence in a batch waits for the slowest one,
  and every sequence was still running to the 4096-token cap. After the
  schema fixes: **9.5 minutes for the same 8 patients**, ~4x faster.
  Extrapolated full-run estimate: ~6.8 days at `generation_batch_size=4`
  (untested whether a larger batch size reduces this further — a sweep
  job was queued at the end of this session, not yet resolved).
- **Real GWDG quota crisis, not hypothetical.** HOME hit 106.25 GiB (177%
  of the 60GB soft limit, 88.5% of the 120GB hard limit, ~9 days left in a
  **2-week grace period** — confirmed via GWDG's own docs that grace-period
  expiry restricts writes the same as hitting the hard limit, regardless
  of hard-limit headroom). Freed ~31.6GB via safe cache cleanup (`pip
  cache purge`, `conda clean --all`, a stale Rust build cache, two stale
  Stage 2 checkpoint directories no longer needed post-training). Real
  fix: moved MedGemma's 51GB weights off personal HOME entirely onto
  KISSKI project storage (`/mnt/vast-kisski`, 5TB, <1% used) via `rsync`
  (verified byte-identical before deleting the original) — HOME dropped to
  ~2.2GB for the repo itself, durably fixing the problem rather than
  band-aiding it.
- **GitHub repo renamed and transferred**: `benniby/20260401_Thesis` →
  `ThesisNovaSBE/three-layer-readmission-audit` (org created by benniby
  specifically to give the user full owner-level access instead of
  collaborator access). Local remote and README clone instructions
  updated to match.
- **Full independent audit run as a fresh agent** (explicitly no context
  from this session, per user's request) covering technical correctness
  and thesis-methodology soundness across the whole repo. 5 critical, 6
  significant, 4 minor findings, plus a "what's solid" section. User
  correctly pushed back on two "critical" findings as not real problems
  (the thesis `.tex` being unwritten and RQ2 being unanswered are both
  just the expected state of a project whose Stage 3 run hasn't completed

  citation-count claim, unverifiable without the literature-review
  teammate's own materials). The rest were independently re-verified (not
  just trusted) against the actual repo state before acting on them.
- **Verified and fixed from the audit**: `requirements.txt` had no upper
  bound on `transformers` — confirmed live that neither of two local Mac
  environments (a stale `.venv` at `5.12.1`, the actively-used conda env
  at `5.16.1`) match the cluster's working `4.57.6`, and this exact class
  of break already cost real time this session. Added `<5.0`. The RQ2
  headline comparison (`evaluate_pipeline.py`'s full-cohort vs.
  control-arm precision/recall) had no confidence intervals, unlike RQ1's
  correctly-implemented paired bootstrap — wired in patient-clustered
  `bootstrap_ci` (discovered this is meaningfully slow at ~104k-admission
  scale due to `bootstrap.py`'s per-group `np.where` loop — not fixed this
  session, flagged for later). Extracted the one genuinely new, previously
  untested piece of the batching rewrite (`_detect_truncated`, the
  per-sequence EOS-based truncation check) into a pure function with 5
  unit tests using hand-built token-ID arrays — no model/GPU needed,
  deliberately not the audit's suggested tiny-real-model approach (user
  correctly questioned whether that was actually necessary; the real
  cluster smoke test is already stronger evidence than a synthetic model
  would be). Fixed three stale doc sentences that contradicted their own
  document's body (an outdated banner date, a "pending the retrain"
  sentence after the retrain had finished, a "fairness analysis is
  planned" sentence sitting below two already-executed fairness tables).
- **User flagged, correctly, that the grounds taxonomy's real-world
  behavior needs checking before committing multi-day compute to it** —
  reframed from the audit's more abstract "disclose as a thesis
  limitation" framing into a practical pre-flight check. Read through the
  full prompt/taxonomy and found two things worth being aware of, not yet
  independently confirmed against real output at scale: `decision_model`
  vs. `decision_rule` will disagree often *by design* (the prompt asks the
  LLM to weigh whether aggravating grounds "contradict" mitigating ones;
  the code-side `decision_rule` mechanically requires zero aggravating
  grounds for an override) — not a bug, but worth knowing before
  interpreting results; and `strong_discharge_support` may be
  over-triggering on generic discharge boilerplate rather than genuine
  evidence of its full three-part definition (follow-up arranged AND
  caregiver present AND clinically stable) — a real, if not yet
  quantified, methodological risk. User was still deciding how to proceed
  on this as of this log.
- **A real-data sanity check for the new bootstrap CI wiring turned into
  its own finding.** Ran `evaluate_pipeline()` end-to-end against the real
  ~104k-admission Stage 1 test partition to confirm 2.2's fix actually
  works — it was still running after 27+ minutes of CPU time. Root cause:
  `bootstrap.py`'s patient-clustered resampling does `np.where(group_of ==
  g)[0]` in a Python loop per sampled group per resample, which scales
  very badly with many unique patients. Killed the slow real-data run and
  added fast synthetic-data tests instead (`tests/test_evaluate_pipeline.py`,
  4 new tests, <1s total) — these actually give *better* correctness
  coverage than the slow run would have (a completed real-data run only
  confirms "didn't crash," not "computed the right thing"; the synthetic
  tests check exact CI properties: point estimate matches, CI contains the
  point estimate, `groups=None` skips CI for backward compatibility, and a
  single-cluster case has deterministically zero-width CI). The underlying
  `bootstrap.py` performance issue is real and unfixed — will add several-
  minutes-plus overhead to every future full-population `evaluate_pipeline.py`
  run.
