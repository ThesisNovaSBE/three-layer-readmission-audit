## Key decisions / findings

- **Stage 1's SLURM script had a bug that only surfaced after 9 hours of
  real, successful compute**: `scripts/slurm_stage1_tune.sh` passed `--mode
  full` to `src.model.evaluate`, which has no `--mode` argument -- only
  `--model`. Python's argparse silently treats an unambiguous prefix as an
  abbreviation, so `--mode` resolved to `--model`, and `'full'` isn't a
  valid model name, crashing with exit 2. The 400-trial tune + final train
  had already completed successfully by the time this hit -- fixed by
  simply dropping `--mode` from that line (evaluate.py reads mode from the
  saved artifact automatically).
- **Stage 1 completed for real**: AUROC 0.7215, AUPRC 0.3965, beats 3 of 4
  published benchmarks cited in `evaluate.py` (LACE, Xiao 2018, Fraccaro
  2016; behind Rajkomar 2018). Confirmed the documented "v1 recall gap" is
  real and specific to age 70+ (recall 19.0% vs 35-45% for other bands) --
  directly validates why the Stage 2 oversampling fix (session 22) mattered.
  All living docs (`MODEL_CARD.md`, `README.md`, `docs/MODELING_PLAN.md`,
  `docs/THESIS_NARRATIVE.md`, `results/README.md`) updated with these real
  numbers; `results/xgboost_metrics.json` added as the first permanent
  snapshot in that directory.
- **A real KISSKI credit-limit scare, resolved as a GWDG-side accounting
  bug, not a real shortage.** `sbalance` showed `kisski-nova-rpcl` at
  3.74/3.75 Mcore-hr used -- alarming given the account's only user
  (`u29346`)'s actual job history only accounted for ~6,400 core-hours.
  Investigated via `sacct`/`sacctmgr` (confirmed single-user account, full
  job history summed to ~42.7 real GPU-hours ever) before escalating.
  Separately, a genuine project-expiration notice arrived (project would
  stop allowing compute in ~1 month, well before the December thesis
  deadline). Sent two support emails; GWDG confirmed the credit number was
  wrong on their end (their own check showed 0.01/3.75 Mcore-hr, matching
  the real usage) and granted a project extension to 31 January 2027.
  Lesson: verify alarming infra numbers against independently-computable
  ground truth (here, real job history) before treating them as fact.
- **Real Stage 2 training completed via early stopping, NOT the pessimistic
  worst case.** A smoke test measured 2.42s/training-step, extrapolating to
  ~60h for 10 full epochs -- but the real run's `EarlyStoppingCallback`
  (patience=3) stopped it at ~1.02 epochs (~15.7h) once validation AUPRC
  peaked and started declining. Real Val AUPRC=0.372, AUROC=0.704. Lesson
  reinforced for the user: more epochs is not unconditionally better once
  compute stopped being the constraint (a real question asked this
  session) -- early stopping exists specifically to find the point past
  which more training hurts, not just saves time.
- **CRITICAL bug caught live: `calibrate.py` reused a stale calibration
  file from a different model.** After the real retrain, the pipeline's
  `calibrate` step printed "Loading existing calibration" -- it had found
  the pre-existing `models/stage2_calibration.json` (a leftover, effectively
  from before this retrain) and reused it untouched, purely because the
  file existed, with no check that it matched the newly-trained model. This
  is the exact staleness-bug class already fixed twice in session 22
  (splits caching, checkpoint resume) -- missed in the one remaining spot.
  Fixed the same way: `train.py` now writes a `stage2_model_fingerprint.json`
  next to the saved model; `calibrate.py` compares against it before
  trusting any cached calibration, recomputing if the model doesn't
  verifiably match (including when no fingerprint exists at all, e.g. an
  older model that predates this check).
- **Built `scripts/slurm_stage2_finish.sh`** to recompute calibration and
  redo predict/evaluate/pipeline-eval/RQ1-comparison against the
  already-trained model, without re-invoking `train_stage2()` -- resubmitting
  the full `train_stage2.sh` would have resumed from a checkpoint and kept
  training past where early stopping had already correctly cut it off. Took
  two attempts to size the time budget right (3h was ~20min short given the
  measured population-wide scoring pass; bumped to 6h, completed in 4h40m).
- **First real Stage 1 vs Stage 2 RQ1 result**: `compare_layers.py`, scoring
  both models independently on the identical 62,759-admission notes-covered
  population (neither gating the other) -- **AUROC 0.7093 (Stage 1) vs
  0.7101 (Stage 2), diff +0.0008 [-0.0041, +0.0054]**. The CI straddles
  zero: a genuine null result, explicitly anticipated and reportable per
  this project's own docs ("a null result here is expected and
  reportable"), not a failure of either model.
- **Current cascade (Stage 1→Stage 2 prune only, no Stage 3 yet) doesn't
  beat matched-budget Stage 1 alone**: full-cohort pipeline (precision
  0.437, recall 0.347, F1 0.387) is nearly identical to the control arm
  (Stage 1 alone at the same 15.1% alert rate: precision 0.431, recall
  0.352, F1 0.388). Expected and incomplete, not concerning -- Stage 3 (the
  actual value-add "auditor" layer) hasn't run yet, so this isn't the real
  RQ2 answer.
- **Repo-hygiene bug found on the same day the finish-up job ran**: the
  checkpoint-staleness fix (session 22) renames a stale checkpoint dir to
  `stage2_checkpoints_stale_<timestamp>/` -- the `.gitignore` pattern only
  matched the literal `stage2_checkpoints/` name, so the renamed dir's small
  metadata files (not caught by the `*.pt`/`*.safetensors` patterns either
  -- `*.pth` specifically wasn't ignored) slipped into a commit. No actual
  model weights were committed. Fixed the gitignore pattern
  (`stage2_checkpoints*/`, added `*.pth`) and untracked the files that had
  already slipped through.
- **Stage 3 rebuilt on a new serving stack.** The existing design (Ollama +
  phi4-mini, `src/stage3/explain.py:call_llm`) was a deliberate laptop-CPU
  choice that stopped making sense once Stage 3's batch run moved to
  cluster GPU hardware. Researched two questions before touching code:
  (1) Ollama vs. native serving on KISSKI -- Ollama can technically run
  without root on a SLURM cluster, but it would be genuinely new, untested
  infrastructure (this session's whole throughline has been eliminating
  exactly that risk class) and architecturally wrong for a ~9,800-call
  batch (no continuous batching, ~3x slower than vLLM at scale per
  published benchmarks); (2) model choice -- compared Phi-4, Gemma
  3/MedGemma, Llama 3.x, Qwen2.5, and clinical fine-tunes (BioMistral etc.,
  found to carry a real, documented instruction-following degradation risk
  from medical continued-pretraining). Landed on **vLLM + MedGemma-27B-text-
  it**: the only candidate with a direct benchmark result on MIMIC-IV-style
  reasoning (AgentClinic-MIMIC-IV), and vLLM's guided/structured decoding
  preserves the schema-constrained JSON generation Ollama's `format=`
  provided (bare `transformers.generate()` has no equivalent -- would have
  reintroduced the malformed-JSON risk that feature specifically solved).
  Checked MedGemma's Health AI Developer Foundations license directly
  (fetched the actual terms + Prohibited Use Policy, not just secondary
  summaries) -- confirmed compatible with this project's academic,
  no-clinical-deployment scope.
- Implemented the swap in `src/stage3/explain.py`: vLLM is lazily imported
  (inside `_get_engine()`/`call_llm()`, not at module level) specifically so
  the rest of the module -- prompt building, response parsing, quote
  verification, none of which touch model serving -- stays importable and
  testable without vLLM installed, since vLLM is GPU/Linux-only and can't
  even install on the Mac this project is otherwise developed on. A
  module-level engine cache (`_ENGINE_CACHE`) ensures the 27B model loads
  once per process, not once per patient (call_llm runs thousands of times
  in a batch). Renamed `cfg.stage3.ollama_model` -> `cfg.stage3.model_name`
  (now a local path, same offline-compute-node pattern as Stage 2's
  Clinical-Longformer) across every reference in `explain.py`, `batch.py`,
  `pipeline.py`, tests, and `config.yaml`.
- Built the cluster-side pieces: `download_stage3_model.sh` (login-node,
  gated-model HF auth via `$HF_TOKEN`, downloads only safetensors shards,
  resumable) and `scripts/slurm_stage3_batch.sh` (preflight checks
  including real weight-file verification, `--resume` always passed since
  `batch.py` writes each result incrementally -- a timeout here loses at
  most one in-flight call, not the whole run, unlike Stage 2's
  calibrate/predict steps which had no incremental persistence). Real
  MedGemma-27B download completed on the cluster (51GB, 11 safetensors
  shards) and a 10-patient smoke test (`--limit 10`) was queued at the time
  of this log -- not yet confirmed working end-to-end.
