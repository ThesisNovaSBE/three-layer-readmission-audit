## What I worked on

Made Stage 1's GPU request actually do something. `scripts/slurm_stage1_tune.sh`
has always requested an A100 node, but `src/model/models.py` built XGBoost
with `tree_method="hist"` and no `device` param — CPU-only regardless of the
hardware it ran on, so the GPU sat idle the whole job. Added a real
`stage1.device` (cpu|cuda) config option, wired it through the one place
(`build_estimator`) that both the Optuna search and the final fit already
funnel through, and fixed a second, more consequential bug found while
touching the same function: the GPU-trained artifact needs to still load and
predict on the user's CUDA-less Mac (`api.py`, `evaluate_pipeline.py`,
`stage3/pipeline.py` all `joblib.load()` it locally) — so the final fit now
resets the estimator to `device="cpu"` after training, before it's saved.

Also found and fixed, while in the same file: `tune.py`'s Optuna study was
never actually persisted (`optuna.create_study()` with no `storage=`), so
the SLURM script's own comment claiming "resumable if preempted" was false —
a preemption on a real multi-hour cluster job would have silently lost the
whole search. Now backed by a sqlite DB with `load_if_exists=True`, and
`run_study` computes how many trials are already recorded before deciding
how many more to run, so resubmitting after a preemption continues toward
the same 400-trial target instead of restarting or silently doing nothing.

## Key decisions made

- GPU device is a config/CLI option (`stage1.device`, `--device`), not a
  hardcoded branch — defaults to `cpu` (Mac-safe, current behavior
  unchanged) unless explicitly overridden. Matches the existing pattern
  for other hardware-dependent settings (Stage 2's bf16/fp16 block).
- Clarified to the user before making this change: GPU doesn't improve
  model quality, it only changes how fast the same 400-trial search
  completes — worth stating plainly since "get the best results possible"
  was the stated motivation and doesn't actually follow from switching
  devices.
- The CPU-reset-after-fit fix only applies to the *final* estimator
  (`train.py:_fit_final_estimator`), not the transient per-fold estimators
  built during CV/tuning (`cv.py:fit_predict_fold`) — those are never saved
  or shipped anywhere, so there's nothing to make portable.
- Left `scripts/slurm_stage1_tune.sh`'s `--time=08:00:00` unchanged rather
  than guessing a new estimate now that the GPU is genuinely used — no
  measured GPU wall-time exists yet for this workload.
