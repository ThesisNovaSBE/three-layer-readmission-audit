### 1.3 The validation controls the project's own docs call load-bearing have zero executed output

Three automated controls exist as code but have never been run at any sample size, and one planned human-validation study has not even been scaffolded:

Per `src/stage3/batch.py:390-392`, the blind-note control is described *in the code itself* as "the most important single check we run" — it has not been run once.
- **Human-clinician Cohen's-kappa validation** (`docs/STAGE3_VALIDATION.md`) has **zero implementation**, not even scaffolding: `docs/validation_cases.csv`, `docs/validation_labels.csv`, `docs/validation_report.md` (the three output files the plan specifies, lines 129-133) do not exist, and no `kappa`/`cohen` string appears anywhere in `src/` or `tests/` (confirmed by grep). The plan document states plainly: "the thesis must report how well it agrees with human clinical judgment — otherwise the population-level finding has no validity anchor" (`docs/STAGE3_VALIDATION.md:22-24`).

**What would resolve this:** Run D1/D2/D3 on a "tens to low hundreds" sample (per the functions' own docstrings) once a full or partial batch run exists, and report the decision-distribution shift and self-agreement rate as real numbers. Absent both, the thesis has no external check that the auditor is reading the note rather than pattern-matching on Stage 1's score, and no check that it agrees with a clinician at any rate — this is a bigger gap than the RQ2 point estimate itself, because even a small-N result here (e.g. κ=0.55 on 50 cases) would materially change what claim the thesis can honestly make.

### 1.4 Dependency pinning gap has already manifested locally, not just hypothetically

`requirements.txt:12` pins `transformers>=4.36` with **no upper bound**. This constraint exists **only as a code comment** — it is not encoded in `requirements.txt` as an upper bound, and there is no lockfile or cluster-specific pinned requirements file anywhere in the repo (`find . -iname "*requirements*"` returns only the one loose file).

**Verified live, not just from the docs:** the project's own local `.venv` currently has `transformers==5.12.1` installed (checked via `pip freeze`) — already past the documented safe ceiling. A second, separately-managed environment on this machine has `transformers==5.16.1`, `torch==2.13.0`. Neither matches "the cluster's transformers==4.57.6" that the Stage 3 code depends on.

**What would resolve this:** Add `transformers<5.0` (or the exact cluster version) as a hard ceiling in `requirements.txt`, and/or commit a cluster-specific pinned lockfile (`pip freeze` from the working KISSKI environment) that `download_stage3_model.sh`/`scripts/slurm_stage3_batch.sh` install from explicitly, rather than the loose floor-only file. Given this project has already lost multiple days to exactly this class of break (Ollama→vLLM→HF migration triggered by driver/library incompatibilities), an unpinned dependency file is a live landmine, not a theoretical risk.

## 2. Significant — should address

### 2.1 Frontend still silently gates on Stage 2's threshold, contradicting the documented architecture — confirmed still live

`docs/ARCHITECTURE.md` states Stage 2's `stage2_confirmed` is "not the final word on a patient" (§2) and the backend was updated accordingly: `api.py:349` defaults `confirmed_only: bool = False`. But `frontend/src/api.ts:24` independently defaults `confirmedOnly = true`, and every call site in `frontend/src/App.tsx:28,50,63` omits an override — so the demo UI silently filters the displayed patient list down to Stage-2-"confirmed" admissions only, the exact opposite of the documented design. This was flagged as a known gap in session 17 ("Needs an actual frontend change plus a browser check... not done this session," `docs/ARCHITECTURE.md:306-311`) and **confirmed still unresolved** on the current HEAD by direct code inspection, not just by trusting the doc's own "not done" note.

**What would resolve this:** Change `frontend/src/api.ts:24`'s default to `false` (matching the backend), or pass `confirmedOnly: false` explicitly from `App.tsx`, then confirm in a browser that the patient list count matches `api.py`'s unfiltered count.

### 2.2 RQ2's headline pipeline comparison has no confidence intervals

`src/model/evaluate_pipeline.py` — the module producing the control-arm-vs-cascade comparison already being quoted in `MODEL_CARD.md:154-156` ("Pipeline, full cohort... precision=0.437... Control arm... precision=0.431") — never calls `bootstrap_ci` (confirmed by reading the whole file; the only import from `src.model.calibration`/`src.model.metrics`, no `src.model.bootstrap` import at all). `docs/ARCHITECTURE.md:465-467` confirms this is a known, still-open gap. By contrast, RQ1's `compare_layers.py` does this correctly with a *paired* bootstrap (§4, "what's solid"). As it stands, the sentence "the control arm is nearly identical to the full pipeline" (`MODEL_CARD.md:158-161`) is a bare point-estimate comparison (0.437 vs 0.431 precision, 0.347 vs 0.352 recall) with no stated interval — it is currently impossible to say whether this is a real null finding or noise around two very close numbers.

**What would resolve this:** Wire `bootstrap_ci` (patient-clustered, `subject_id`) into `_pipeline_report`/`_control_arm_report`, and report the precision/recall/F1 differences with CIs the same way `auroc_diff_stage2_minus_stage1` already is in `comparison_rq1.json`.

### 2.3 The actual LLM-calling code path has zero automated test coverage

`tests/test_stage3_batch.py` patches `src.stage3.batch.call_llm_batch` directly (`_patched_batch`, lines 96-110) — the real function (`src/stage3/explain.py:738-872`, containing the left-padding setup, `prefix_allowed_tokens_fn` wiring, and the `eos_id not in row.tolist()` truncation-detection logic that was hand-verified only against a real cluster smoke test) is never exercised by any test, even with a fake tokenizer/model stub. All ~45 tests in `tests/test_stage3_explain.py` thoroughly cover the pure functions (`_parse_response`, `compute_decision_rule`, `verify_quote`, `build_prompt`, `compute_discordance`) — that coverage is genuinely good — but the newest and least-exercised code (the 2026-09-15 batching rewrite) is exactly the part with no regression protection. This matches the audit brief's concern about mocking hiding real bugs: a future edit to `call_llm_batch` (e.g., changing padding side, or the EOS/pad-token defaulting logic) could silently break batched generation and the test suite would still report green.

**What would resolve this:** A unit test using a minimal fake `PreTrainedModel`/tokenizer (or a tiny real local model such as `sshleifer/tiny-gpt2`) that exercises `call_llm_batch`'s tokenization/padding/truncation-detection logic end-to-end without needing the real 27B model or a GPU.

### 2.5 Discordance threshold remains provisional and currently unvalidatable

`config.yaml:236` sets `discordance_displacement_pp: 20.0`. Both the code (`src/stage3/explain.py:166-169`) and `docs/ARCHITECTURE.md:166-169` are honest that this is "a provisional value; validate empirically... before reporting it as a result — nobody has done this yet." `sweep_discordance_thresholds` is implemented and unit-tested as a pure function, but `run_sensitivity_sweep` (`src/stage3/batch.py:311-341`) requires `stage3_batch_results.csv` to exist — so, per Finding 1.2, this constant cannot currently be validated even if someone tried today. Any thesis sentence describing "≥20pp is discordant" needs an explicit "provisional, not yet swept" caveat until the sweep is actually run.

### 2.6 Grounds-taxonomy circularity is a real design tension, not currently named as a limitation

`MITIGATING_GROUNDS`/`AGGRAVATING_GROUNDS` (`src/stage3/explain.py:94-108`) are a fixed, 10-category, human-authored list. `_validate_grounds` (`explain.py:512-526`) hard-fails the entire response if the model cites anything outside this list — "don't let the model invent categories" is an explicit design choice for parseability/auditability, and a defensible one. But it also means the auditor can only ever surface findings the taxonomy's authors anticipated in advance, which is in tension with the "independent judgment" framing the thesis is built around (`docs/THESIS_NARRATIVE.md:21-27` — "reaches its own judgment"). None of `docs/ARCHITECTURE.md`, `MODEL_CARD.md`, or `docs/THESIS_NARRATIVE.md` names this tension explicitly as a limitation to disclose in the thesis; it should be, in the Limitations section, alongside a concrete falsification criterion (e.g., "the free-text `clinical_justification` field should occasionally reference clinically relevant content that maps to no fixed ground — if it never does across a large sample, that is itself evidence the taxonomy is doing the real work, not the LLM's judgment").

## 3. Minor / polish

### 3.1 Attention-span sentence alignment is approximate, undocumented as such
`src/stage3/attention.py:_sentences_by_attention` (lines 50-87) re-tokenizes each sentence independently and assumes concatenated per-sentence token counts align with the whole-note tokenization; on any subword/whitespace divergence it silently `break`s (line 81) with no logging, truncating which later sentences are even eligible for the top-n auxiliary hint. Since this is explicitly auxiliary-only, never load-bearing for the decision (per the module's own Jain & Wallace caveat, lines 9-14), this is low severity — but a one-line docstring caveat ("may under-cover long notes due to sentence/token alignment drift") would prevent a reader from assuming full-note coverage.

### 3.2 Silent note-load failures on the on-demand (API) path only
`src/stage3/pipeline.py:_load_note_text` (lines 127-144) catches all exceptions and returns `""` with no logging. This is exactly the failure mode that hid the real bug fixed in commit `2148937` (wrong target column silently producing empty notes for every explanation). The batch path (`batch.py:_preload_notes`) does not have this problem — it has no swallowing try/except — so the risk is scoped to the single-patient on-demand API path only, but a one-line `print`/log on the exception would make any repeat of this bug class immediately visible instead of silent.

### 3.3 Human-validation sample size is thin per stratum
`docs/STAGE3_VALIDATION.md:26-34` plans N=50 total (15 CONCORDANT / 20 NOTE_MITIGATES / 15 NOTE_AMPLIFIES) for the three-way κ. Reasonable for an overall estimate, but flagged now (before the annotation effort is spent) that any per-stratum breakdown of agreement will have wide, likely-uninformative CIs at n=15-20.

### 3.4 CMS-methodology scope gap already well-disclosed internally but not yet in the thesis
`docs/ARCHITECTURE.md:548-554` already discloses that the cohort does not exclude OBSERVATION-type stays from the readmission count, unlike CMS's measure. This is handled well internally (disclosed, not silently assumed away) — it just needs to migrate into the thesis's own Limitations section once that section is written (see Finding 1.1).

## 4. What's actually solid

- **Leakage-free, fingerprint-verified splits.** Stage 2's fine-tuning population is built strictly from Stage 1's own `train_idx` (`src/stage2/splits.py:82`), patient-level (`subject_id`), with a SHA256 fingerprint of `train_idx` + target column cached and checked before any split/calibration cache is trusted (`_splits_fingerprint`, `_load_cached_splits_if_fresh`). This is not just a design claim — it caught two real staleness bugs live in this project's own history (checkpoint resume, session 22; calibration reuse, session 23, commit `0cb9a07`), each fixed with the same general mechanism rather than a one-off patch. This is genuinely good engineering discipline, repeatedly demonstrated under real pressure, not just asserted.
- **RQ1's statistics are done correctly.** `src/model/bootstrap.py` implements proper patient-clustered bootstrap resampling (verified correct on read), and `src/model/compare_layers.py:_paired_auroc_diff_ci` uses a *paired* bootstrap for the Stage1-vs-Stage2 AUROC difference rather than the common mistake of subtracting two independently-resampled CIs — this is explicitly called out as a deliberate choice in the code and is statistically correct.
- **Reproducibility enforcement for Stage 3 is real, not just claimed.** `stage3.temperature` (default `0.0`) is read in exactly one consequential place (`do_sample = cfg.stage3.temperature > 0`, `explain.py:842`), with no CLI override path anywhere in the codebase that could silently defeat it — confirmed by a full-repo grep, not just by reading the docstring.
- **No PHI, no MIMIC data, no credentials in git history.** Verified directly (not just via `.gitignore` inspection): a full `git log --all --diff-filter=A --name-only` search found no committed `.csv`/`.parquet`/MIMIC-pattern files, and a full `git log --all -p` regex search for common API-key/token patterns (`hf_...`, `sk-...`, AWS-style keys) returned nothing. The one real git-hygiene slip this project had (stale-checkpoint metadata slipping past an incomplete `.gitignore` pattern) was caught and fixed the same day, with the pattern durably widened (`stage2_checkpoints*/`, `*.pth`).
- **The RQ2 control arm is a genuinely well-motivated comparison.** Thresholding Stage 1 alone to match the full system's realized alert rate (`evaluate_pipeline.py:_control_arm_report`) is exactly the right check to prevent the standard mistake in cascade papers (an apparent precision gain that's actually just a tighter alert budget) — it's implemented, wired into every pipeline evaluation run by default, and explicitly documented as load-bearing.
- **Percentile-rank discordance is a well-reasoned methodological choice.** Using rank displacement instead of raw `stage2_score - stage1_score` specifically to be invariant to unequal residual calibration error between two different model families is correct reasoning, has a passing invariance-to-monotonic-rescaling unit test (`test_discordance_invariant_to_monotonic_rescaling`), and the rationale is clearly and correctly stated in both code and docs.
- **Quote verification is a genuine, cheap anti-hallucination mechanism.** `verify_quote` mechanically checks every extracted ground's quote against the actual note text; it can't catch a misleading-but-verbatim quote, but it does catch fabricated evidence, which is a real, checkable guarantee most "LLM cites its sources" designs don't bother to enforce in code.
- **Claims about test/lint status verified true, not just trusted.** `pytest` (151 passed, 1 skipped) and `pylint` (10.00/10) were run directly during this audit and match what the docs claim.
- **Self-critical documentation culture.** Across `docs/ARCHITECTURE.md`, `MODEL_CARD.md`, and the session logs, this project is unusually honest about what hasn't been done yet (RQ2 pending, controls not run, discordance threshold provisional) — the gaps found in this audit are, almost without exception, gaps the project's own docs already flag, just not always with the finality the thesis submission will require. That honesty is itself worth preserving as the project moves from internal engineering docs into the actual thesis text.
